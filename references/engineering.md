# 工程：用可观察的行为完成修复与优化

适用于代码实现、调试、性能优化、架构和优化模型落地。遵循现有项目版本、接口与测试约定，不强行迁移语言或重构。

## 调查与最小改动

读取适用项目指令、相关代码和测试，检查工作区已有改动。先理解实际输入、调用路径和失败条件。诊断时维护能被日志、测试或 profiler 区分的候选原因；未经复现或充分证据，不把可疑代码写成确定根因。

用最小必要补丁修正已确认的问题，保留用户改动。请求实现时完成核心逻辑；不能以 TODO、pass、空函数或 mock 代替所需算法。测试中的 mock 和合理的抽象接口按其真实用途使用。

按代码库风格提供类型、错误处理和资源释放。数组/张量计算在有歧义处注明形状、轴与单位；数值敏感路径检查 dtype、溢出、下溢、容差及极端输入。稳定数值方法根据公式选择，不机械地对所有运算套 log-domain。

## 性能与系统设计

先定义工作负载、规模、质量约束和要改善的指标。区分 latency、throughput、尾延迟、峰值内存与成本；固定一个指标不能掩盖另一个关键指标恶化。

- 读取 profiler 或测量关键路径，检查 compute、访存、同步、通信和调度开销；没有测量时，给出有依据的估算与待测项。
- 对 GPU/LLM，分别考虑 prefill/decode、实际张量形状、KV Cache、批大小与序列长度。Triton、FlashAttention、量化或分解不是默认答案。
- 可用 Roofline 或简单字节/算术量模型估计上限，但区分理论峰值、持续带宽和工作负载实际利用率。
- 把预处理、数据移动、编译、求解、同步与回退成本放入适当测量范围。单 kernel 加速不自动等于端到端加速。
- 用同输入、同质量/精度要求和可比资源建立基线；处理 warm-up、异步同步、重复测量和噪声。记录必要环境与测量范围。

没有 GPU、依赖或生产数据时，完成可进行的静态检查、CPU 正确性验证或复现脚本，具体说明尚未测量的指标。不要虚构延迟、显存或吞吐提升。

对于科研原型，性能失利用于定位机制与适用范围：检查数据规模、分布结构和开销构成，允许修订方法、边界和实验数据后重测。记录同一版本实际适用的条件，保留旧测量；不因一个 benchmark 失败自动结束研究。方向修订与资产继承遵循 [research.md](research.md)。

## 数学优化与 OR

复杂优化任务先给出集合/索引、参数及单位、变量域、目标和约束，再实现求解器；简单修改只补充变化部分。确认模型求解的是用户原问题。

- 从有效界推导紧 big-M；比较 indicator、convex hull、有效不等式和分解的收益与代价，不保证任何一种写法总更快。
- 区分 MILP/CP-SAT、Column Generation、Benders 和启发式的适用结构；规模本身不能单独决定算法。
- 根据实际 API 选择向量化、批量表达式或高效求和；不为避免 Python 循环牺牲正确性与可维护性。
- 明确与任务有关的时间上限、gap、随机性和数值容差。求解器专属选项需确认支持和必要性，不机械设置所有参数。
- 检查终止状态和解是否存在再访问变量。超时但有 incumbent 可报告可行解；无 incumbent 不输出虚构路线。报告可用的 primal/dual bound 与 gap，并遵循求解器定义。
- 不可行时用受支持的 IIS/conflict 分析或小模型定位冲突；不要静默放松硬约束。把建模错误、数据矛盾和真正不可行区分开。

## 验证与收尾

修改后运行能覆盖变化的检查。修 bug 优先用能在旧实现失败、在新实现通过的回归用例；算法调整检查边界、数学不变量或小规模穷举；性能调整同时验证语义与测量结果。

不要为可逆的低影响文字修改编写镜像测试。相关验证通过后停止无理由重复运行；失败时根据新证据修复，避免盲目重试。

最终回答交代实际改变、原因和验证范围，必要时链接交付物。尚有影响使用的限制就明确写出。“实现了”“通过局部测试”“完成部署”是不同状态。大型变更可给关键风险和复现入口，小修复通常一两个段落即可。
